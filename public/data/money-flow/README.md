# Money Flow demo data

Powers the interactive at [/software/where-did-my-money-go/](https://skoonkor.github.io/software/where-did-my-money-go/),
which is a small re-implementation of the Money Flow screen in
[Where Did My Money Go?](https://github.com/SKoonkor/WhereDidMyMoneyGo).

`seed.json` is generated by [`tools/build_money_seed.py`](https://github.com/SKoonkor/skoonkor.github.io/blob/main/tools/build_money_seed.py).

## Where it comes from

It is not anybody's ledger, and it is not made up either.

Inventing a plausible two months of spending by hand is harder than it sounds, and the
result always reads as invented: the daily counts come out too even, the categories too
balanced, and the fixed bills land on suspiciously round dates. What makes a money chart
convincing is not the amounts but the **rhythm** — rent once a month and nearly six
times the next-largest thing bought, food two fifths of the rows and a sixth of the
money, savings moving in the week after payday.

So the generator takes that rhythm from a real ledger and discards everything else:

| kept | discarded |
|---|---|
| daily transaction counts | every note and description |
| the share of rows each category takes | the amounts (re-denominated, then jittered ±18%) |
| which day of the month the fixed bills land on | the exact dates (moved ±2 days within their month) |
| the ordering of income, spending and transfers | outliers, clipped at each category's 90th percentile |
| the account structure | the account names, mapped onto the app's defaults |

Categories with fewer than four rows in the window are folded into `Other`. Rows sharing
a day, an account and a category are merged into one — which is also what the app's own
hold-to-read readout does when it groups repeats, and without it the chart is 315 bars
over 57 days — five and a half a day — which at ten pixels a day on a phone is a grey
smear rather than a chart. Rent is the one exception: it keeps its own row rather than
merging into Bills, because it is the figure the page names.

The random seed is fixed, so rebuilding produces no diff. It is also a constant in a
script this page links to, so the jitter is reproducible by anyone who wants to: what
actually protects the source is the merging, the clipping and the fact that the original
ordering is not published. Salary and rent are not jittered at all — they are standing
figures, and moving them by a fifth between two months on screen reads as a bug.

## Shape

```jsonc
{
  "meta":     { "currency": "GBP", "symbol": "£", "start": "…", "end": "…" },
  "accounts": [ { "name": "Bank Accounts", "opening": 1075.00, "savings": false } ],
  "sign":     { "Income": 1, "Expense": -1, "Transfer-In": 1, … },
  "buckets":  { "needs": [ … ], "wants": [ … ], "targets": { … } },
  "categories": { "Expense": { "Bills": ["Rent", …] }, "Income": { … } },
  "txns":     [ { "id": 4, "period": "2026-07-01", "account": "Bank Accounts",
                  "type": "Expense", "category": "Bills", "subcategory": "Rent",
                  "amount": 506.50 } ]
}
```

**Amounts are unsigned.** Direction lives in `type`, through the `sign` map, exactly as the
app stores it. An `Expense` of 42 and an `Income` of 42 are both `42`. This is worth
copying: the alternative, a signed amount, means every reader and every import path has to
agree about what a negative refund means, and eventually one of them does not.

**A transfer is two rows** sharing a `transferId` — a `Transfer-Out` of the source account
and a `Transfer-In` of the destination. Its `category` holds the *other* account, which is
the app's own convention. Both legs carry the same amount, so a transfer moves a balance
without changing net worth.

**`currency` is one field on the whole file** rather than one per row as the app stores it.
The demo is single-currency, and it saves a column in the ledger under the chart.

**`opening`** is what each account carried into the window. Without it, switching the demo
to the second month alone would start the chart at zero and the whole month would be a
fiction. Asset accounts are lifted just enough that no balance goes negative across the
window; `Credit Card` is a liability and is left negative, because that is what a card is.

## Rebuilding

```sh
python3 tools/build_money_seed.py
```

It reads a SQLite ledger outside this repository and will do nothing without it. The
generated `seed.json` is committed; the source database is not, and never should be.

When `seed.json` changes, **bump `DATA_VERSION` in `src/scripts/explore/data-version.js`
by hand**. It is the cache key for everything under `/data/`, and it is otherwise only
regenerated by the simulation export — so without a bump a returning reader keeps the old
ledger indefinitely.
